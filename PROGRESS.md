- Implemented, after agreeing the three trade-offs with the user (auto-detect with a manual override; switch to the fast models; vendor the assets locally):
  - **`src/lib/ocr.ts`** (new) — owns everything Tesseract. A pool sized to `hardwareConcurrency - 1` capped at 4, with staged warm-up (first worker awaited so the rest hit warm caches instead of racing to download the same ~4 MB core). For `'auto'`, one probe worker per language recognizes the first scanned page concurrently and the highest mean-confidence language wins the document; below a confidence/character-count floor it falls back to all three, which is slower but can't be wrong.
  - **`usePdfParser`** — now two passes. Pass one reads every text layer; pass two renders and OCRs the pages that had none, six in flight across the pool. The pool is *started* (not awaited) the moment the first scanned page is seen, so its multi-megabyte start-up overlaps reading the remaining text layers. Render scale is now target-DPI-based (150 DPI) with a 4-megapixel ceiling, replacing the blind 2x — typical A4 renders as before, but the oversized fold-out pages common in scanned government documents no longer produce tab-stalling bitmaps. Blank pages are detected from a 64x64 downsample and skipped. `page.cleanup()` after every page.
  - **`public/tesseract/`** — the wasm cores and trained data, vendored by a new `npm run vendor:tesseract`. OCR previously pulled ~10 MB from jsDelivr at runtime; a CDN request for `mar.traineddata` also leaks what kind of document is being read, which contradicts the app's own footer text.
  - **`OcrLanguageSelect` / `useOcrLanguage`** — the manual override, persisted to `localStorage`, threaded through `useDocumentIndex` via a ref (not a dependency, which would only churn the effect).
- **Measured, not estimated.** Built a browser benchmark over eight dense voter-roll-shaped Devanagari pages (3-column grid, 30 entries/page, Devanagari names and addresses plus Latin EPIC-style codes) and compared the old configuration against the new on the same images:

  | configuration | worker start-up | recognition | total |
  |---|---|---|---|
  | old: 1 worker, eng+hin+mar, `best_int`, from CDN | 3,434 ms | 21,341 ms | 24.8 s |
  | new: pool of 4, mar+eng, `fast`, same-origin | 393 ms | 7,105 ms | **7.5 s** |
  | new, but keeping all three languages | 397 ms | 8,264 ms | 8.7 s |

  So **~3.3x**, not the order of magnitude first estimated — and the credit is distributed differently than expected: the pool and the fast models do nearly all the work, while cutting the language count is worth only ~14%. Most of a page's OCR cost turns out to be layout analysis, not running each language's model. The old start-up figure is also flattered by a warm CDN cache; a genuinely cold browser would be far worse.

Hindi and Marathi documents routinely carry Latin text — voter ID codes, place names, form numbers — so this would have quietly broken a real search. Measured the fix on the sparse fixture, where Devanagari-only vs Devanagari+English was 1,200 ms vs 1,236 ms — ~3% — and the Latin text came back exactly right. Devanagari documents are now always recognized with English alongside, on both the auto and the manual path (the manual path had the same bug on first implementation, found by testing each override rather than just the default).

**Known issues:**
- Text-layer parsing and page rendering still run on the main thread; OCR itself no longer does.
- PDF extraction of Devanagari can drop/garble characters within complex conjunct clusters, traced to how the source PDF's font was subset/mapped to Unicode. Not fixable client-side; DOCX is unaffected.
- OCR remains the slowest thing the app does — ~3x faster than before, but a many-page scanned document still takes tens of seconds on the CPU in the browser.
- Forcing a document language the document isn't in loses that document's text entirely, with no warning. Correct for an explicit override, but unguarded.
